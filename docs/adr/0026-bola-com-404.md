# ADR-0026: Autorização por objeto, e o recurso de outro cliente responde 404

- **Status:** Aceita
- **Data:** 2026-10-28

## Contexto

Com o login (ADR-0024), cada serviço sabe **quem** pede e **o papel**. Falta a pergunta que mais
derruba API no mundo: **a conta pedida é de quem pede?** No OWASP API Security Top 10 ela é a
número 1, **BOLA** (*Broken Object Level Authorization*): a Ana, logada como cliente, troca o id na
URL por o da conta do Bruno e lê o saldo dele. O papel está certo (ela é cliente); o objeto não é
dela.

E o que responder? **403** ("proibido") confirma que a conta existe — e o id vira algo que dá para
testar em massa até achar contas válidas. **404** ("não encontrado") é a mesma resposta de uma conta
que não existe: não revela nada.

## Decisão

Todo recurso de cliente confere o **dono** e, se não for de quem pede, responde **404**, com o
mesmo corpo de "não existe":

- **O dono** vem do token: o claim `cliente_id`. Quem não tem vínculo (um cliente sem
  `cliente_id`) não é dono de nada.
- **Analista e serviço** não têm dono a conferir (leem tudo). Isso é decidido na aplicação
  (`PermissaoDeLeitura`, `Acesso`), não no controlador.
- **contas:** cliente, conta e contas do cliente — conferido contra o `clienteId` da conta.
- **extrato:** o extrato não sabe o dono (ele se monta só dos eventos do razão). Ele pergunta ao
  contas (`GET /v1/contas/{id}/titular`, com token de serviço) e guarda a resposta num cache com
  limite de tamanho e **sem prazo**: o dono de uma conta não muda. Se o contas estiver fora do ar,
  o cliente recebe **503** com `Retry-After` (não dá para afirmar que a conta é dele); analista e
  serviço não dependem do contas.
- **pix:** enviar Pix (a conta pagadora é de quem pede), consultar transferência, listar, registrar
  e excluir chaves, QR Code. A consulta de chave (o "DICT") é para qualquer cliente: é o que mostra
  o nome de quem recebe antes de confirmar — com a chave mascarada.
- **A checagem vem antes do banco** sempre que dá: um pedido de outro dono não custa uma consulta.

**Prova reversa** (o teste que prova que o teste prova algo): tirar a checagem de cada serviço
faz os testes de autorização falharem — no contas, `contaDeOutroEhComoSeNaoExistisse` e `semVinculo`
passam a receber 200; no extrato, 1 teste de unidade e 3 de integração; o código foi restaurado
depois. O E2E confere o mesmo pelo BFF, no navegador: a Ana pede cinco endereços da conta do Bruno
e recebe 404 em todos.

## Alternativas consideradas

- **403 para o que é de outro** — mais "honesto", mas confirma que o id existe.
- **Checar só no gateway** — o gateway não sabe o dono de uma conta; e um serviço que confia no
  gateway fica aberto para quem chega por outro caminho (outro serviço, a rede interna).
- **Ids impossíveis de adivinhar e nada mais** — os ids já são UUID aleatórios; isso ajuda, mas não
  é autorização: um id vaza num log, num print, numa URL compartilhada.

## Consequências

- **Positivas:** a regra mais explorada de API fica coberta em todo serviço, com prova reversa; o
  404 não ajuda quem testa ids.
- **Negativas:** o extrato passa a depender do contas para o cliente (mitigado pelo cache e pelo
  503 explícito); um 404 para "é de outro" deixa o suporte sem saber, só pela resposta, se a conta
  existe — ele usa o backoffice, que vê tudo.
